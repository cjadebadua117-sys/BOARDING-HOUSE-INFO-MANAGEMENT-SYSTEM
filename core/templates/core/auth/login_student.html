It is built as the reference form the client asked for: one curved colour ground with an invitation on each side, and the two forms riding across it — press "Create account" on the colour and the ground sweeps to the other half while the registration sheet slides in behind it. Nothing about the swap is a client-side trick: the server still renders both real Django forms, still decides which one is live (initial_mode) and still re-renders the page with a failed POST's errors sitting in the sheet that owns them. With no JavaScript the visitor gets the sign-in sheet and the invitation button does nothing — which is why the no-JS fallback is the safe half. The back-end routes are unchanged, so every bookmark, POST target and ?mode=signup link keeps working. {% endcomment %} {% block auth_title %}{% if initial_mode == 'signup' %}Create your account{% else %}Sign in{% endif %}{% endblock %} {% block auth_style %} {% endblock %} {% block auth_layout %}

Exactly one is live per mode — the one that is NOT the mode you are in ("New here?" while signing in) — and the other is parked off the canvas. The parked one is marked inert and given a dead tab stop here, in the markup, so that a screen reader gets the same story even if the script never runs; the deck's script keeps exactly that pairing from then on. Both presses are plain links for the same reason: with no script they go to the page that renders the half they name, and with a script they trade the halves in place instead.{% endcomment %}
